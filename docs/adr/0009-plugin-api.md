# ADR-0009: Plugin API

- Status: Accepted and implemented, 2026-10-12 (lane 11); amended the same day after the lane's independent verification (the sandbox's allowlist, the page's policy over each sandbox, the parsed source check, grants bound to the files enabled); amended 2026-10-13 (lane 16, resource hardening: the serialize-once transport and the message budget); amended 2026-10-13 (lane 17, permission consistency: what each permission really lets through)
- Deciders: the maintainer (the behaviour below was decided before the lane); the lane-11 builder (how the sandbox, the host and the batches work)
- Source: the lane-11 brief; ADR-0001 (every change is a transactional op), ADR-0003 (one front end for the browser and the desktop), ADR-0005 (components and the editing context), ADR-0006 (the cut list)

## Context

SketchUp's value to woodworkers is half its extensions: cabinet makers, joinery tools, reports. Sawhorse should be extensible the same way, but without the failure modes people know from extension ecosystems: an extension that hangs the app, corrupts the model, phones home, or reads files it was never meant to. Sawhorse runs as a static site in a browser tab and as a Tauri desktop app from the same build, so whatever runs a plugin must work in both, with no native code and no server.

## Decision

**Behaviour (decided before the lane):**

- A plugin is a folder (or a .zip of it) with `plugin.json` (`id` reverse-DNS, `name`, `version`, `api: 1`, `description`, `author`, `license`, `permissions`, `contributes` {commands, panels, tools, menus, shortcuts}, `entry`) and an ES-module entry.
- Every plugin runs in its own Web Worker, with no DOM and no window, and talks to the app only through a typed message RPC with request ids, timeouts and a watchdog. A crashed or stuck plugin never takes the app down. Identical in the browser and the desktop app.
- Permissions are declared, shown before enabling and enforced by the app: `model.read`, `model.write`, `ui`, `storage` (per-plugin, app- and document-scoped), `file` (host pickers only), `net` (an explicit allowlist of origins, lane 17; no `fetch` otherwise). `importScripts` and loading outside code are blocked.
- The API (`api 1`) is typed by an in-repo package, `packages/plugin-api`: model reads and transactional, named batch writes (one undo step, through the existing op set and the kernel's validator), a declarative panel UI, tools that receive pointer events, inference and Value Control Box input like the built-in tools, notifications, prompts and confirms, units, pure geometry, events and storage.
- Loading: installed plugins (desktop `<app data>/plugins/<id>/`), Install from .zip, Load unpacked folder (desktop) or Load from .zip for this session (browser), enable, disable, reload, uninstall; three bundled samples, listed but off until enabled; a Plugins pane, a Plugins menu, plugin panels as collapsible sections, plugin tools in the rail's plugin group.

**How it is built:**

- **The package** (`packages/plugin-api`): `index.d.ts` declares the `"sawhorse"` module with each call's permission; `sawhorse.js` is the shim plugins import (it hands out the API the sandbox installed under `Symbol.for("sawhorse.plugin-api")`); `manifest.schema.json` and `src/manifest.ts` (one validator for the app and `npm run plugin:check`); `src/source.ts` (the source rules); `src/rpc.ts` (the protocol and a plain-data codec); `src/runtime.ts` (the plugin side: batches, placeholders, callbacks, events); `src/geometry.ts`. Pure TypeScript with erasable syntax, so Node runs the validators directly.
- **The sandbox** (`src/plugins/sandbox.worker.ts`, `lockdown.ts`): one module Web Worker per plugin. Before plugin code loads, the worker's global object, and the prototypes it inherits from up to `EventTarget`, are cut down to an **allowlist** (`ALLOWED_GLOBALS`): the language's built-ins, `WebAssembly`, and web APIs that compute without reaching anything (text encoding, URLs, blobs, streams, `Response` bodies, crypto, timers, offscreen canvas). Everything else is deleted: `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `WebTransport`, `FontFace` and `fonts`, `importScripts`, IndexedDB, Cache Storage, the origin private file system, the webkit sandboxed file systems, nested workers, `BroadcastChannel`, `MessageChannel`, `postMessage`, `Notification`, and any API a later browser adds. `navigator` keeps only facts (`ALLOWED_NAVIGATOR`); `URL.createObjectURL` goes too. Every way to turn text into code is disabled: `eval`, `Function` and its async and generator forms (the constructors stay recognisable, `f instanceof Function` holds, but they throw), and string timers. With `net`, a mediated `fetch` comes back. (Amended after the lane's verification: the first version removed a blocklist of names and missed `FontFace`, whose `load()` fetched any URL from a plugin without `net`, and `webkitRequestFileSystemSync`, an origin-wide file system any plugin could write. An allowlist fails closed.)
- **The page's policy governs the worker**: `workerChannel` (`src/plugins/host.ts`) starts each sandbox from a `blob:` module that imports the sandbox script by its absolute URL. A worker started from a `blob:` URL takes the policy of the page that made it; one started from its own URL takes its response's headers, which a static host cannot set. The browser build writes its policy into `index.html` (`vite.config.ts`, `cspMeta`: scripts from the app and `blob:` only, fonts from the app and `data:` only, no objects); the desktop app's is in `tauri.conf.json` (the tag is left out of the Tauri build, whose policy Tauri sends with the page). `npm run site:check` refuses a demo without it.
- **Linking without loading**: the app sends the plugin's module texts; the sandbox checks them again (`checkPackage`), turns each into a blob URL with its import specifiers rewritten to the blob URLs of the modules it names (or the shim's), in dependency order, and imports the entry. A module may import only `"sawhorse"` and its own files by a relative path; dynamic `import()` (and any `import.<phase>` form) and `importScripts` are refused statically. Each module is **parsed as an ES module with acorn** and the rules are read from the syntax tree (`ImportExpression`, `MetaProperty`, the static import and export declarations, with the specifier as the loader reads it); a module the parser cannot read is refused. (Amended: the first version scanned the text with comments and strings blanked and guessed regex versus division from the previous token; a regex holding a quote after `if (...)`, `throw`, `delete` or `export default` hid an `import()` from it.) With the runtime locks above and the policy, no code can arrive later from anywhere.
- **The host** (`src/plugins/host.ts`, `manager.ts`): every request names a method, every method needs one permission (`METHODS`), and the manifest grants it or the request fails with code `permission` before anything else looks at it. Events are delivered only when subscribed to and allowed. A ping each second; no answer for 5 s is "not responding" (with Stop); 15 s is stopped (a pause of the app's own thread longer than three pings restarts the count: the plugin could not be heard in it). A worker error is a crash; contributions go with the plugin. Requests are rate- and size-limited; logs are rate-limited.
- **Model writes are named batches with placeholders** (`sawhorse_kernel::refbatch`): a plugin sends a name and ops; any value may be `{"$ref": i, "path": "regions.0"}`, a value an earlier op of the batch produces. The ops are resolved against a scratch copy of the model op by op; the resolved list is applied as one plain `Op::Batch` to a second copy and its outcomes compared with the scratch ones (a divergence is refused, never applied with a wrong id); then it is applied to the document. One undo step, the validator on the result, logged as plain ops that replay anywhere. No new kernel op was needed. The app names the undo step ("Undone: Generate cabinet") by remembering which depth and model hash a plugin batch produced.
- **Panels are data**: a checked list of fields (`src/plugins/panel.ts`) drawn by the app's components; no plugin markup reaches the page. Images are `data:` URLs of image types only.
- **Plugin tools are tools**: `PluginTool` (`src/tools/plugin.ts`) sits in the same `ToolDriver`, gets the same resolved events (pick and inference), forwards them to the worker (pointer moves coalesced) and draws what the plugin asked for, checked: the app's colours only, finite points, bounded sizes. Tool ids are `plugin:<plugin id>/<tool id>`. (Amended, lane 17: the resolved events are the model, so they reach only a plugin with `model.read`. `PluginManager.toolCall` rebuilds every `tool.event` for a plugin without it from the pointer alone (`src/plugins/toolEvent.ts`): `type`, `x`, `y`, the modifiers and the eye ray, `picked: null`, and `snap: null` or the point the tool's own inference constraints give for the ray (its locked line's nearest point, its plane's crossing), worked out from the ray and those values only. The marker shows that point. A `ui` plugin could make its tool the active one and read the snap's ids and positions as the person moved the mouse; that was model reading without the consent for it.)
- **Storage**: app-scoped in localStorage (256 KB per plugin); document-scoped in memory, written into the `.shz` as `plugin-data.json` on save and read back on open (readers ignore entries they do not know, so the format version is unchanged; `docs/format.md`).
- **Where plugins live**: desktop folders under `$APPDATA/plugins` (the fs plugin's appdata scope), unpacked folders added to the fs scope by the dialog, "Open folder" through a Rust command that opens only a folder holding a `plugin.json`; browser installs in IndexedDB. Enabled plugins and their grants in localStorage. **A grant is bound to the package enabled**: its SHA-256 over every file's path and contents (`packageDigest`, with a small synchronous SHA-256 in `src/lib/sha256.ts`), its source and, for an unpacked folder, the folder (`grantMatches`). Other files under the same id (an update, a replacement zip, a zip claiming a bundled sample's id) are off until the person enables them again, and the dialog names the sample one replaces; a new version asking for more says what is new. A bundled sample keeps its grant across app updates and an unpacked folder across Reload, because the person chose the source and not a build. (Amended: grants were keyed by id alone, so a same-id zip with the same permissions, even one replacing a bundled sample, started at once on the old grant.)

**The transport (amended, lane 16).** Messages were structured clones checked by the receiver after the browser had already copied them: a plugin could make the app hold 400 MB with one `storage.set` of 100 references to a 4 M-character string (each value was within its limit; nothing limited the total), copy a 1.5 GB buffer behind a 1-byte view (the limit measured the view, the clone copies the buffer), loop the app 2^32 times over a sparse array, or pass every sender-side check and change the data before it was cloned (a getter read twice). Now:

- **Serialize once.** The sender (the plugin's runtime, or the host) serializes each message once, with intrinsics taken before any plugin code ran, into one `ArrayBuffer` (`packages/plugin-api/src/wire.ts`: a small header with the kind, the id and the method, then one value in a tagged binary form), and transfers it. Getters are read once, a view sends only its own bytes, holes and extra list properties are refused, `__proto__` keys are refused.
- **Measure before reading.** The receiver accepts only a plain `ArrayBuffer` (not shared, not resizable) and checks its `byteLength` against the budget for its kind and method (4 MB by default; 34 MB for `file.save` and the answer to `file.open`; 12 MB for `net.fetch`; 24 MB for the modules at start) before reading anything. It then reads the values out of the bytes with every limit applied before allocating: a count the remaining bytes cannot hold is refused, strings are checked by their byte length before decoding (UTF-8, strictly), byte arrays are copied into their own buffers, keys are at most 256 characters.
- **Answer, never drop.** A request the host cannot read or will not take is answered with a typed refusal (`"too_large"`, `"invalid"`, `"busy"`); an answer the host cannot fit in the budget is replaced by such a refusal; a frame the sandbox cannot read settles the pending call with a `PluginApiError` of the same code (it used to be logged and dropped, leaving the plugin waiting forever).
- **Rate and work.** The host keeps a token bucket per plugin (300 messages a second, bursts of 100; ten seconds' worth in one second stops the plugin), measures the time it spends on each plugin's messages (250 ms a second for five seconds stops it), caps batches a second and work in flight per method, and aborts a plugin's queued batches, dialog and downloads when it stops. See `docs/PLUGINS.md` (The message budget) and `docs/LIMITS.md`.

**What each permission lets through (amended, lane 17).** A review of every path by which data or effects cross between a plugin and the app, against what the enable dialog says, found nine places where the two differed. Each is fixed where the data leaves the app, with a regression test that fails on the old code:

- **Tool events (F1).** A plugin tool's pointer events carried the inference engine's snap and the pick (solid and face ids, vertex positions, face frames), so a `ui` plugin could make its tool the active one and read the model as the person moved the mouse. `PluginManager.toolCall` now rebuilds every `tool.event` for a plugin without `model.read` from the pointer alone (above, *Plugin tools are tools*). Requiring `model.read` for any tool was the other choice; it would have made a pointer-only tool (a measuring overlay, a drawing aid working on its own plane) ask to read the whole model.
- **Files (F2).** In a browser without the File System Access API (Firefox, Safari, `?io=basic`), or when the save picker failed for a reason other than a cancel, `file.save` downloaded at once: no dialog, a name and type the plugin chose. Now the app asks first in its own dialog (`DialogRequest` `download`: the plugin, the file name, the size), and names that would run when opened (`BLOCKED_SAVE_EXTENSIONS`, or ending in a dot or a space) are refused. `file.open` without transient user activation is refused with code `user_activation` (a file input clicked without it never settles, and held the plugin's one `file.open` slot for good); every request carries its own abort signal, and one waiting on the person (`WAIT_LIMITED`: saves, opens, prompts, confirms) is given up after `waitMs` (5 minutes) with code `timeout`, its dialog closed, its picker's answer dropped.
- **The network (F3).** The allowlist compared the host name alone: `localhost` let a plugin send POST, PUT and DELETE to every local port, and `api.example.com` reached any port of it. An entry is now one origin (`parseNetEntry`, `originAllowed`): a host is https on port 443, `https://host:port` and `http://localhost:port` are exactly that, plain `localhost` is any port of it and the dialog says "any port on localhost". A wildcard on a public suffix (`*.vercel.app`, `*.github.io`, `*.co.uk`, every plain top-level domain: a short list, `PUBLIC_SUFFIXES`, extended by hand) is refused by the validator: with `model.read` it was an exfiltration path to anyone's site there. An answer without a stream used to be cut to the cap and passed on; it is refused.
- **The selection (F4).** `model.select` changes what the person's next Delete or Move acts on; it stays under `model.read` (a plugin that reads the model usually wants to point at what it found), and the dialog now says "and change the selection".
- **Write without read (F5).** A refused batch's reason names the model ("no face #12 on object 7"), so a plugin with `model.write` alone could read through it; it now hears only the failing op's index and a generic reason (`batchRefusedWithoutRead`). A successful batch's outcomes (the ids it made) still come back: placeholders and later batches need them, and they name only what the plugin made.
- **Attribution (F6).** A tool's status line and hint start with the plugin's name, like `ui.notify`; a plugin may not be named "Sawhorse" or "Sawhorse ..." (`reservedName`: case, NFKC, invisible characters and common look-alike letters folded), since every dialog says "from <name>".
- **The page's own hooks (F7).** `window.__sawhorse.plugins.enable` granted a whole manifest with no dialog to any script in the page. It is compiled only where `__SAWHORSE_TEST_HOOKS__` is true (the dev server, vitest, `SAWHORSE_TEST_HOOKS=1`); `npm run build` and `npm run site:check` fail a build that has it (`scripts/check-test-hooks.mjs`), and Playwright serves its own build with it (`scripts/e2e-serve.mjs`, `dist-e2e/`).
- **Grants (F8).** A grant changed only on Enable, so a source that keeps its grant across changes (a bundled sample, an unpacked folder) could drop a permission and ask for it again later with no dialog. A grant now records the `net` entries shown with it and, whenever it holds for the files added, shrinks to what they ask for (`trimGrant`); asking for more, a permission or a host, needs the dialog.
- **Lookups (F9).** The method and event tables and a tool view's colour and lock kind are read by own keys (`Object.hasOwn`): `"constructor"` was a colour (a function), and a refusal could print a function's source as the permission a method needed.

- **A batch's limits hold while it is built** (found by the lane's full end-to-end run, a flake of lane 16's hostile-plugin test, about one run in four on `main` too). Its attack adds a million ops to one batch; `b.op` serialized every one (4.5 s of the plugin's own thread, no answer to the watchdog's pings) before the commit was refused, and on a loaded machine that passed 15 s and the watchdog stopped the plugin mid-test. The runtime now throws `too_large` at the op past 2,000 (`BATCH_MAX_OPS`, the app's and the kernel's `MAX_OPS`) or past the 4 MB a message holds, at once (13 ms). The test's expectations are unchanged.

What was already consistent and stays so: requests are checked against `METHODS` before anything else; events are delivered only when subscribed and allowed; storage is scoped to the manifest's id; files come back as names, never paths; there is no `fetch` without `net`; panel images are `data:` URLs; batches are checked before the kernel sees them.

## Consequences

- A plugin cannot freeze, crash or corrupt the app: it runs in its own thread, every write goes through the kernel's validator as one transaction, and a refused batch changes nothing (the fuzzer checks this for 10,000 sequences, docs/DEVELOPMENT.md).
- The op log stays the single source of history: a plugin's batch is ordinary ops, so `.shz`, autosave, replay, goldens and the fuzzer need nothing new. A batch that draws and pulls a box hashes exactly as the built-in tools' box (`crates/kernel/tests/refbatch.rs`).
- The desktop window's content security policy now allows `blob:` scripts (`script-src 'self' 'wasm-unsafe-eval' blob:`): that is how a plugin's modules are linked in its worker, and how each sandbox is started. The app itself creates no blob scripts outside the plugin sandbox. The browser build has a policy too (it had none): the same `script-src` and `font-src`, a wide `connect-src` (granted `net` requests are made by the page, and the render service may be elsewhere), `object-src 'none'`. A violation-free walk through the panes and the samples is a Playwright test (`e2e/csp.spec.ts`).
- Three independent locks keep a plugin in: the parsed source check, the allowlisted global object and the page's policy. Each is tested on its own in Playwright: the verifier's bypasses refused by the check, the verifier's `FontFace` exfiltration failing with nothing reaching a live listener, and a raw `blob:` worker (no lockdown, no check) unable to load an outside font, an outside module or a `data:` module under the policy.
- `acorn` (MIT, no dependencies) is a runtime dependency: about 120 kB minified in the main bundle and the sandbox worker.
- `net` is mediated by the app's `fetch`. The desktop window's `connect-src` does not include outside hosts, so on the desktop a `net` plugin's requests are refused by the policy until the shell gets a mediated HTTP path (an open question; no sample needs the network).
- A plugin's own copies of `Array.prototype` and friends are its own: it can only confuse itself, since everything it says is checked again by the app.
- Not yet: a plugin directory, signing and update checks; plugin-defined inference; per-instance attributes for plugins (a plugin tracks what it made by id in its document store); plugin access to scenes, tags and styles beyond the ops; `net` on the desktop.
- Clean room: SketchUp's extension behaviour (Ruby console, extension manager, menus, tools, dialogs) was described from memory as a user knows it; no SketchUp Ruby API source or extension code was read. See `docs/CLEANROOM.md`.
